# Лабораторная работа 6 — Decorator (структурный паттерн)

## 1. Тема и цель

**Тема:** паттерн Decorator («Декоратор»).
**Цель:** научиться наращивать поведение объекта обёртками, не изменяя сам объект и не плодя подклассы.

Сюжет лабы: есть «голый» LLM-клиент, который только ходит в модель. Поверх него нужны прод-функции — логирование, повтор при сбоях, кэширование. Все они наращиваются декораторами.

## 2. Теория

**Decorator** — структурный паттерн, который позволяет динамически добавлять
объектам новое поведение, помещая их внутрь объектов-обёрток.

Ключевая идея: обёртка (декоратор) реализует **тот же интерфейс**, что и
оборачиваемый объект, и **хранит ссылку** на него. Вызов метода у декоратора
сначала (или после) выполняет добавленную логику, а затем делегирует вызов
внутрь. Декораторы можно вкладывать друг в друга — получается «матрёшка».

Чем отличается от наследования: наследование фиксирует поведение на этапе
компиляции и порождает комбинаторный взрыв классов (лог+кэш, лог+retry,
кэш+retry, лог+кэш+retry…). Декоратор собирает любую комбинацию в рантайме
из мелких независимых классов — принцип открытости/закрытости (OCP):
новое поведение = новый класс, существующий код не трогается.

## 3. Участники паттерна в лабе

| Участник GoF | В коде | Роль |
|---|---|---|
| Component (интерфейс) | `ILlmClient` | общий контракт: `Complete(string prompt)` → `ChatResponse` |
| ConcreteComponent | `FakeLlmClient` | ядро — только ходит в «модель», ничего не знает об обёртках |
| Decorator (база) | — (нет абстрактного базового класса) | в C# при одном методе абстрактный слой не нужен: каждый декоратор сам реализует `ILlmClient` и хранит `_inner` |
| ConcreteDecorator | `LoggingDecorator`, `RetryDecorator`, `CacheDecorator` | добавляют по одной функции |

## 4. Схема цепочки

```
        вызов Complete("…")
              │
              ▼
        ┌───────────┐    кэш-попадание: ответ сразу, дальше НЕ идём
        │   Cache   │──►(hit)──► результат с FromCache = true
        └─────┬─────┘
              │ (miss)
              ▼
        ┌───────────┐    до 3 попыток; сбой ловит и пробует снова
        │   Retry   │
        └─────┬─────┘
              │
              ▼
        ┌───────────┐    печатает "-> промпт" и "<- N ток."
        │  Logging  │
        └─────┬─────┘
              │
              ▼
        ┌───────────┐    каждая 2-я попытка бросает TransientLlmException
        │ FakeLlmClient
        └───────────┘
```

## 5. Разбор кода (Program.cs)

**Контракт и данные**

```csharp
public sealed record ChatResponse(string Text, int Tokens, bool FromCache);

public interface ILlmClient
{
    ChatResponse Complete(string prompt);
}
```
Запрос — просто строка, ответ — record. `FromCache` — флаг, позволяющий
наружному коду отличить ответ из кэша от «живого».

**Ядро**

```csharp
public sealed class FakeLlmClient : ILlmClient
{
    private int _calls;

    public ChatResponse Complete(string prompt)
    {
        if (++_calls % 2 == 0)                       // каждая 2-я попытка «падает»
            throw new TransientLlmException("сетевой сбой шлюза");

        return new ChatResponse(...);
    }
}
```
Имитация похода в модель: детерминированно падает каждую вторую попытку, чтобы
на демо было видно работу Retry. Бросает `TransientLlmException` — «временный»
сбой, который имеет смысл повторить (в отличие, скажем, от ошибки авторизации).

**Декоратор 1 — логирование**

```csharp
public ChatResponse Complete(string prompt)
{
    Console.WriteLine($"    [log] -> \"{prompt}\"");
    var response = _inner.Complete(prompt);
    Console.WriteLine($"    [log] <- {response.Tokens} ток.");
    return response;
}
```
Классическая схема декоратора: сделать что-то ДО, делегировать внутрь, сделать
что-то ПОСЛЕ. Строки `[log]` печатаются только когда запрос реально дошёл до
ядра — по этому признаку в выводе видно кэш-попадание.

**Декоратор 2 — retry**

```csharp
for (int attempt = 1; ; attempt++)
{
    try
    {
        return _inner.Complete(prompt);
    }
    catch (TransientLlmException ex) when (attempt < _maxAttempts)
    {
        Console.WriteLine($"    [retry] попытка {attempt} не удалась: {ex.Message}");
    }
}
```
Тонкое место: фильтр исключений `when (attempt < _maxAttempts)`. На последней
попытке catch не срабатывает, и исключение само вылетает наверх — не нужно
писать отдельный `throw`. Ловим только `TransientLlmException`: постоянные
ошибки ретраить бессмысленно.

**Декоратор 3 — кэш**

```csharp
if (_cache.TryGetValue(prompt, out var cached))
    return cached with { FromCache = true };   // модель не дёргаем

var response = _inner.Complete(prompt);
_cache[prompt] = response;
return response;
```
`cached with { FromCache = true }` — неразрушающее копирование record: кэш
хранит «чистый» ответ, а флаг подставляется только в отдаваемую копию.
Важно: попадание в кэш **не доходит** до Retry и Logging — вся обвязка
пропускается.

**Сборка матрёшки в Main**

```csharp
ILlmClient client = new CacheDecorator(
    new RetryDecorator(
        new LoggingDecorator(
            new FakeLlmClient()),
        maxAttempts: 3));
```
Порядок сборки имеет смысл: Cache снаружи — потому что кэшированный ответ
не должен тратить попытки и засорять лог; Retry внутри Cache — потому что
повторять надо только промахи кэша; Logging ближе всех к ядру — логирует
каждую физическую попытку, включая повторные.

## 6. Что показывает запуск

```
Цепочка: Cache -> Retry(3) -> Logging -> FakeLlm

    [log] -> "Привет, кто ты?"
    [log] <- 15 ток.
— "Привет, кто ты?" -> OK [от модели] виртуальный ответ на "Привет, кто ты?"

— "Привет, кто ты?" -> OK [из кэша] виртуальный ответ на "Привет, кто ты?"

    [log] -> "Расскажи про Decorator"
    [retry] попытка 1 не удалась: сетевой сбой шлюза
    [log] -> "Расскажи про Decorator"
    [log] <- 17 ток.
— "Расскажи про Decorator" -> OK [от модели] виртуальный ответ на "Расскажи про Decorator"
```

Разбор по пунктам:

1. **Первый вопрос** — промах кэша → запрос прошёл через Logging в ядро,
   вернулся ответ, припоминается в кэше.
2. **Второй вопрос (тот же промпт)** — кэш-попадание: ответ вернулся сразу
   со сноской `[из кэша]`, и **ни одной строки `[log]` нет** — Retry и Logging
   не выполнились вообще.
3. **Третий вопрос** — первая попытка упала на ядре (счётчик дошёл до чётного),
   Retry поймал сбой, повторил — вторая попытка успешна. Итого два прохода
   через Logging при одном вопросе.

## 7. Ключевые моменты для защиты

- Все декораторы реализуют `ILlmClient`, поэтому клиент ничего не знает,
  во что он «завёрнут» — он видит просто другой `ILlmClient`.
- Поведение собирается в **рантайме** из независимых классов; чтобы добавить,
  например, ограничение бюджета, пишем один новый декоратор и оборачиваем
  цепочку снаружи — ни один существующий класс не меняется (OCP).
- Порядок декораторов влияет на семантику: поменяйте Cache и Retry местами —
  и кэшировать станут каждую повторную попытку, а попадание в кэш перестанет
  пропускать логи.

## 8. Вопросы, которые часто задают на защите

**— Чем Decorator отличается от наследования?**
Наследование статично: для комбинации «лог+кэш+retry» пришлось бы завести
класс-потомка. Декоратор комбинирует поведение в рантайме из мелких классов,
каждый из которых делает ровно одну вещь.

**— Чем Decorator отличается от Chain of Responsibility?**
Внешне похожи (цепочка объектов с одинаковым интерфейсом), но в Decorator
**все** звенья выполняют свою логику вокруг вызова, а в CoR запрос движется,
пока его **не обработает одно** звено, остальные пропускаются. Декоратор
добавляет поведение, CoR распределяет ответственность.

**— Почему у декораторов нет общего абстрактного базового класса?**
Он был бы нужен, чтобы вынести общее состояние (`_inner`) и делегацию. Здесь
у каждого декоратора ровно один метод, поэтому общий слой ничего бы не
сэкономил — в C# это допустимое упрощение, при расширении контракта базовый
класс `LlmClientDecorator` появляется естественно.

**— Что будет, если ядро бросит постоянную (не transient) ошибку?**
Retry её не поймает (фильтр по типу исключения) — исключение выйдет наружу.
Это осознанно: повторять, например, невалидный запрос бессмысленно.

**— Почему кэш стоит снаружи Retry, а не наоборот?**
Хотим, чтобы закэшированный ответ обходил всю обвязку мгновенно и без логов,
и чтобы повторные попытки при сбое не приводили к многократной записи в кэш.
Порядок обёрток — часть архитектурного решения.
