# Lab11. Visitor (поведенческий)

## Цель
Отделить алгоритмы от структуры объектов: новые операции без правки существующих классов.

## Как работает паттерн
Операция выносится в отдельный класс-визитор. Каждый элемент реализует
`Accept(visitor)`, который просто вызывает `visitor.VisitЭтотТип(this)` —
это двойная диспетчеризация: сначала выбирается метод по типу элемента,
затем по типу визитора. Новая операция = новый класс-визитор; классы элементов
закрыты для изменения. Недостаток: новый ТИП элемента требует дополнить все визиторы.

## Как реализовано
| Сущность | Роль |
|----------|------|
| `IVisitable<TVisitor>` | обобщённая основа: visitable-объект знает тип своего визитора |
| `IChatElement` | доменный интерфейс элемента (наследует `IVisitable<IChatVisitor>`) |
| `IChatVisitor` | интерфейс визитора: по методу `Visit` на каждый тип элемента |
| `ChatVisitorBase` | абстрактная база операций: посещает все типы + `BuildReport()` |
| `UserMessage`, `AssistantMessage`, `ToolCall`, `ImageAttachment` | 4 элемента диалога |
| `TranscriptVisitor` | операция 1: текстовая расшифровка диалога |
| `CostVisitor` | операция 2: тарифы (вход/выход/мегапиксели), суммарная стоимость |
| `JsonVisitor` | операция 3: JSON-экспорт — добавлена без правки иерархии |

Дженерик здесь — `IVisitable<TVisitor>`: любой визитаемый тип привязан к типу
своего визитора на этапе компиляции.

## Демо
Один и тот же список диалога (6 элементов: реплики, tool-call, картинка)
прогоняется через три визитора подряд — иерархия при этом не менялась.
