# Lab5. Proxy (структурный)

## Цель
Показать подмену объекта обёрткой с дополнительной логикой.

## Как работает паттерн
Проблема: настоящий сервис дорогой (задержка сети, деньги за токены), а доступ
к нему надо контролировать и по возможности сокращать.

Решение: прокси реализует тот же интерфейс, что и сервис. Клиент не знает, с чем
работает — с сервисом или обёрткой. Прокси выполняет дополнительную работу
до (или вместо) вызова настоящего объекта. Канонические виды прокси:
remote (стуб), virtual (ленивое создание), protection (контроль доступа),
кеш — виртуальный прокси с умным поведением.

## Как реализовано
| Класс | Роль |
|-------|------|
| `ILlmService` | Subject: общий контракт сервиса и прокси |
| `RemoteLlmService` | RealSubject: задержка 0.6–1.2 с, считает токены и деньги |
| `ProtectionProxy` | Proxy (protection): пускает запрос дальше только с валидным API-ключом |
| `CachingProxy` | Proxy (cache): `ConcurrentDictionary<LlmRequest, Entry>`, TTL, hit/miss-статистика |
| `LlmRequest` | record — равенство по значению, поэтому работает как ключ кеша |

Оба прокси получают настоящий сервис через конструктор — клиент собирает
цепочку сам: `new CachingProxy(new ProtectionProxy(remote, key))` тоже будет работать.

## Демо
1. Protection: запрос с неверным ключом -> `UnauthorizedAccessException`, сервис НЕ вызван;
   с верным ключом -> пробрасывается дальше.
2. Caching: 1-й запрос ~1 с (сеть), тот же повторный — мгновенно (HIT),
   новый вопрос — снова MISS, после истечения TTL — опять сеть.
   В конце статистика и счётчик реальных вызовов.
