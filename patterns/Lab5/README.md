# Lab5. Proxy (структурный)

## Цель
Показать подмену объекта обёрткой с дополнительной логикой.

## Как работает паттерн
Проблема: настоящий сервис дорогой (задержка сети, деньги за токены), а доступ
к нему надо контролировать и по возможности сокращать.

Решение: прокси реализует тот же интерфейс, что и сервис. Клиент не знает, с чем
работает — с сервисом или обёрткой. Прокси выполняет дополнительную работу
до (или вместо) вызова настоящего объекта.

### Канонические виды прокси
| Вид | Смысл | Пример из жизни |
|-----|-------|-----------------|
| remote | заместо находится в другом адресном пространстве | RPC/сетевой стуб |
| virtual | создаёт дорогой объект только когда он реально нужен | ленивая загрузка картинки |
| protection | проверяет права вызывающего | проверка API-ключа, ролей |
| caching | хранит результаты прошлых вызовов | кеш ответов сервера |

В работе реализованы **protection** и **caching** — они нагляднее всего показывают
суть: «тот же интерфейс + доп. логика до/вместо вызова настоящего объекта».

## Как реализовано
| Класс | Роль |
|-------|------|
| `ILlmService` | Subject: общий контракт сервиса и прокси |
| `RemoteLlmService` | RealSubject: задержка 0.6–1.2 с, считает токены и деньги |
| `ProtectionProxy` | Proxy (protection): пускает запрос дальше только с валидным API-ключом |
| `CachingProxy` | Proxy (cache): `ConcurrentDictionary<LlmRequest, Entry>`, TTL, hit/miss-статистика |
| `LlmRequest` | record — равенство по значению, поэтому работает как ключ кеша |

### Детали, на которые стоит обратить внимание
- **Ключ кеша** — сам объект `LlmRequest`: это record, поэтому равенство по значениям
  полей (model + prompt + apiKey + temperature). Один и тот же вопрос с другой
  temperature — это другой ключ -> MISS.
- **TTL** — у каждой записи кеша есть `ExpiresAt`. Просроченную запись прокси
  сам удаляет и идёт к сервису заново.
- **Потокобезопасность** — `ConcurrentDictionary` плюс неизменяемые `Entry`:
  прокси можно дёргать из нескольких потоков без дополнительных блокировок.
- **Цепочка прокси** — оба прокси получают «цель» через конструктор и реализуют
  тот же интерфейс, поэтому клиент может собрать композицию:
  `new CachingProxy(new ProtectionProxy(remote, key))` — сначала проверка ключа,
  потом кеш, и клиент об этом даже не знает.
- **Статистика** — `Hits`, `Misses`, `TokensSaved` в кеширующем прокси и
  `RemoteCalls` в настоящем сервисе позволяют доказать, что экономия реальна.

## Демо
1. Protection: запрос с неверным ключом -> `UnauthorizedAccessException`, сервис НЕ вызван;
   с верным ключом -> пробрасывается дальше.
2. Caching: 1-й запрос ~1 с (сеть), тот же повторный — мгновенно (HIT),
   новый вопрос — снова MISS, после истечения TTL — опять сеть.
   В конце статистика и счётчик реальных вызовов (4 запроса -> 3 вызова сервиса,
   из них 1 на protection-прокси).

## Отличия Proxy от похожих паттернов
- **Adapter** меняет интерфейс, **Proxy** оставляет тот же;
- **Decorator** добавляет поведение, но обычно не контролирует доступ/создание;
  в C# отличить их на коде трудно — различие в назначении;
- **Facade** упрощает работу с подсистемой, а не подменяет один объект.
